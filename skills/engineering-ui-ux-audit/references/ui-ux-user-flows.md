# 用户流程：从漂亮页面到能完成的任务

> 本文件保留任务卡、页面类型矩阵、状态契约、表单、权限、高风险与 AI 长任务说明，供理解背景。
> **逐条评判以 [rules.md](ui-ux-rules.md) 为准。** 对应：任务 `UX-FLOW`；导航 `UX-IA`；表单表格 `UX-FORM`；状态与数据 `UX-STATE`；风险权限 `UX-RISK`；无障碍 `UX-A11Y`。


本文件是本技能的实践扩展，不表示 Eian 的网站目录逐项提出了这些流程规则。参考网站可以帮助发现模式，但模式是否适合当前产品，需要由任务、数据、风险和测试决定。视觉原则见 [visual-system.md](ui-ux-visual-system.md)，量化标准与验证见 [verification.md](ui-ux-verification.md)。

## 1. 先定义完整任务，不只定义页面

用一条可检查的路径描述任务：

> 谁，在什么权限和环境下，从哪里进入，想完成什么，需要提供哪些信息，什么系统结果代表完成，失败或离开后如何继续。

把“点击了提交按钮”与“服务器已经接受并保存”分开。页面状态不能代替事实状态。没有后端可验证时，只能交付界面原型，并标注未接通的部分。

### 1.1 最小任务卡

- **用户与频率**：新手、熟练用户、管理员、访客；一次性还是高频重复？
- **入口与上下文**：列表、深链接、邮件、搜索、浏览器返回；是否带筛选或对象 ID？
- **目标与成功证据**：对象创建成功、结果可找到、文件可打开、状态已更新。
- **前置条件**：登录、权限、库存、网络、数据完整性；缺失时的可行出口。
- **动作边界**：哪些只是本地编辑，哪些会发送、支付、发布或改变权限？
- **中断与恢复**：刷新、后退、关闭、会话过期、断网后保留什么？
- **不变量**：不能重复提交、不能丢已输入内容、不能把旧结果显示为新结果。

界面优化先修明显阻塞，再减少无必要步骤，再做表达和视觉精修。不要为了减少点击而去掉必要审阅、明确同意或重要确认。

### 1.2 页面类型决策矩阵

| 页面类型 | 首要任务 | 应优先优化 | 必测边界 | 容易误判的“优化” |
|---|---|---|---|---|
| 营销落地页 | 理解价值并判断下一步 | 对象、收益、证据、入口与条件 | 长文案、慢图片、无视频、手机 | 用动画和口号替代产品说明 |
| 注册/引导 | 获得最初价值 | 必要信息、进度、可跳过的非必要设置 | 已有账户、邀请失效、验证失败、中断 | 提前索取过多资料，虚构进度 |
| 搜索/目录 | 找到合适对象 | 查询、筛选、排序、结果比较 | 零结果、拼写、长查询、后退恢复 | 搜索一变就丢筛选和滚动位置 |
| 商品/服务详情 | 判断适配与成本 | 规格、可用性、总成本、限制和证据 | 缺货、变体、不同币种、长选项 | 隐藏费用，默认选付费升级 |
| 结算/预约 | 正确提交具体承诺 | 明细、费用、时间、对象、修正入口 | 价格变化、重复提交、超时、失败后查单 | 把未知结果当失败并直接重试 |
| 仪表盘 | 发现状态并定位问题 | 关键指标定义、时间范围、异常与下钻 | 无数据、旧数据、不同权限、异常值 | 大量指标卡却没有可执行含义 |
| 数据表/运营台 | 高效查找与批量处理 | 密度、对齐、筛选、选择范围、反馈 | 大数据、分页、多选、并发变更 | 把表格变成无法比较的大卡片 |
| 编辑器/创建页 | 完成并保留内容 | 输入连续性、保存状态、版本与预览 | 撤销、冲突、失焦、断网、长内容 | 只靠自动保存图标却没有恢复能力 |
| 设置/权限页 | 理解当前配置并安全修改 | 作用范围、当前值、后果和生效状态 | 无权修改、依赖、继承、失败回滚 | 开关样式暗示即时生效但实际未保存 |
| 文档/文章 | 理解与查找知识 | 目录、层级、可读性、搜索和相关内容 | 放大、打印、长代码、深锚点 | 过度动画和悬浮栏遮住阅读内容 |
| AI/长任务界面 | 发起任务并判断结果可信度 | 输入、阶段、停止、结果、来源和下一步 | 部分输出、取消、超时、失效结果 | 将生成过程当完成，把推测显示为事实 |

这些是选择检查项的入口，不要求每页具备所有功能。以真实范围和用户需求裁剪，不凭空增加产品模块。

## 2. 用状态契约补齐页面

为核心组件或流程列出：**状态 → 可见内容 → 可做动作 → 焦点/读屏反馈 → 下一状态**。截图只证明某一状态存在，不能证明转换正确。

| 状态 | 页面应说明 | 可行出口与行为 | 不能做的事 |
|---|---|---|---|
| 初始 | 当前任务、必要输入、默认值来源 | 开始、查看帮助、离开 | 默认代替用户作有代价的决定 |
| 首次空态 | 尚未创建什么、第一步为何有用 | 创建、导入或查看示例 | 写成系统错误或无意义庆祝 |
| 搜索无结果 | 当前条件未命中 | 调整查询、清除具体筛选、返回 | 把查询清空且无法恢复 |
| 权限受限 | 用户可知的限制与可行下一步 | 请求权限或返回可访问范围 | 暴露无权查看的数据、对象存在性或内部规则 |
| 加载 | 正在发生什么，必要时显示范围 | 继续其他任务；长操作可取消 | 每次局部请求都遮住整个页面 |
| 部分加载 | 哪些结果可用、哪些仍在获取 | 保留已可用内容与局部重试 | 把缺失值当真实的零 |
| 空数据 | 数据源确实无记录或范围无数据 | 更改时间范围、建立数据 | 与网络失败使用同一“暂无数据” |
| 局部错误 | 哪一部分失败、是否影响其他内容 | 重试该部分、替代路径 | 清空全部成功结果和输入 |
| 提交中 | 动作正在处理，是否可取消 | 防重复触发，保留上下文 | 允许无保护的重复有副作用请求 |
| 结果未知 | 请求可能已执行，尚未确认 | 查询状态、明确恢复路径 | 显示“失败”并鼓励重复支付/发送 |
| 成功 | 哪个对象完成了什么、后续状态 | 查看、继续、必要时撤销 | 提前乐观宣告不可逆操作成功 |
| 过期/冲突 | 本地与服务端不再一致 | 刷新比较、合并或重新确认 | 静默覆盖他人或用户的新内容 |
| 离线 | 当前信息是否缓存、可编辑范围 | 保存草稿、恢复联网后处理 | 暗示已同步而实际只在本地 |

### 2.1 加载反馈按工作量设计

- 短操作先让控件及时响应，再按实际延迟决定是否出现加载提示；避免每次瞬时响应都闪一下骨架屏。
- 骨架应近似真实布局并预留空间，不必逐像素模拟内容。无法预测结构时，清晰文本反馈比假结构更好。
- 进度可测才给百分比；不可测时说明阶段或正在等待的对象，不编造线性进度。
- 局部更新尽量保留旧内容并明确更新中。不能把旧价格或过期结果不加说明地当作当前数据。
- 重试要有停止条件、次数或显式出口；持续失败后显示可采取的下一步，不无限旋转。
- 上传等长任务明确文件级与整体进度，取消已完成部分和取消剩余部分的区别。

### 2.2 异步一致性与防重复

- 快速改变筛选条件时，旧请求返回不得覆盖新条件结果。用取消或请求身份比对实现，而非只加动画遮掩。
- 防抖可减少请求，但不能使输入失去即时视觉反馈；确认回车、粘贴、中文输入法组合输入和清空操作都正确。
- 提交中按钮状态防止重复点击；真正有副作用的重复保护通常还需要服务端幂等机制。不要把前端禁用按钮说成完整保证。
- 乐观更新适合可恢复、低风险操作，并要求失败回滚、冲突处理和明确反馈。支付、权限授予、外发等不能仅凭本地动画断言成功。
- 表单提交失败保留用户数据，但不应把敏感信息无依据写入 URL、日志或持久存储。
- 浏览器关闭后能否继续、会话跨标签页怎样同步，都必须依据真实实现说明，不能让文案承诺不存在的恢复能力。

## 3. 表单：减少猜测，不替用户做决定

### 3.1 组织与输入

- 每个字段回答“为什么现在需要”。不必要的字段删除或延后，必要字段解释用途。
- 标签始终可见；示例、格式和限制放在输入前能看到的位置。不要等提交失败才告知字数、格式或支持范围。
- 默认值应符合上下文、易发现、易更改；涉及订阅、隐私或额外费用时不以预选冒充用户选择。
- 按有意义的分组组织长表单。分步流程应显示实际步骤、当前进度、可回退范围和是否保存。
- 选择匹配任务的控件：互斥选项用单选，独立选项用复选；开关通常表达即时生效状态，延后统一保存时需明确。
- 手机键盘类型应匹配数据。电话号码、邮编、银行卡末位等不是用于算术的数值，避免数字输入控件丢前导零或引入增减按钮。
- 支持正确的自动填充、粘贴、密码管理器和有帮助的输入属性，不为了“安全感”禁止粘贴。
- 日期输入考虑手输与选择两条路径、时区、地区格式和不可选日期原因。
- 必填与可选标识策略一致，不只靠红色星号。输入提示与错误通过程序化关联能被读屏器获知。

### 3.2 校验时机

1. 用户尚未有机会输入时，避免满页错误。
2. 失焦或提交时指出可修正错误；格式输入中不要反复中断。
3. 用户纠正后及时更新错误，不要求再提交一次才消除已解决提示。
4. 服务端错误与客户端错误表达一致，但不能假设客户端校验取代服务端校验。
5. 多字段失败时保留全部输入，给错误摘要和跳转路径；不要仅用顶部一条“参数错误”。

错误文案包含对象、问题和可行动的修复，例如“结束日期须晚于开始日期，请调整其中一个日期”。不能知道原因时坦诚说明，并提供重试或联系支持的实际路径，不把系统失败归咎于用户。

### 3.3 登录与验证码

[WCAG 2.2 的可访问认证说明](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html)要求避免无辅助的认知功能测试，并列出替代方法、辅助机制等条件。允许密码管理器和粘贴是一条重要实现路径。

- 一次性验证码可以视觉分格，但必须支持整串粘贴、适当自动填充、退格和键盘移动。
- 倒计时、重新发送、过期和错误要区分；不能让用户不知道哪条验证码有效。
- 不把对象识别等标准例外解释为“所有 CAPTCHA 都无障碍”。必须评估真实替代路径和用户群体。
- 不要求优化者在真实用户账户上完成认证、验证码或安全设置变更来“验证设计”；行为权限与界面设计范围分开。

## 4. 导航与交互模式

### 4.1 保留用户位置与上下文

- 面包屑表达层级，返回按钮表达任务历史，两者不一定相同。
- 可分享的筛选、排序和分页可考虑写入 URL，但敏感信息不能因此泄露。刷新与浏览器前进/后退应恢复合理状态。
- 列表打开详情后返回，尽量恢复筛选、分页、选择与滚动位置，避免用户重新找对象。
- 导航和动作使用正确原生元素。普通链接保留复制地址、新标签打开等能力；执行动作不用伪链接。
- 离开有未保存输入的页面时，只在确有丢失风险时提醒，不在无修改时重复阻拦。

### 4.2 对话框与浮层

[WAI-ARIA APG 对话框模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)说明了模态对话框的焦点边界与键盘行为。优先使用已验证的组件实现，再检查业务集成。

- 打开后焦点进入适当位置；长内容可以先聚焦标题或开头，避免直接跳到底部按钮。
- 模态开启时背景不可交互，Tab/Shift+Tab 保持在模态内，Esc 一般关闭，关闭后焦点回到合理位置。
- 关闭不是“成功提交”。关闭、取消、保存和撤销需要明确区分。
- 触发控件已被删除时，焦点回到逻辑上的下一操作位置，而不是页面顶部或隐藏元素。
- 对话框有名称，必要时有说明。内容长或包含复杂结构时，不把全部内容粗暴拼成一个冗长描述。
- 嵌套对话框、全屏小屏对话框和软键盘场景单独测试；能简化为独立页面时，不为保留背景强行层层叠加。

### 4.3 选择合适的模式

| 问题 | 优先考虑 | 边界 |
|---|---|---|
| 页面跳转 | 普通链接/导航 | 不套用菜单的键盘语义 |
| 少量即时命令 | 菜单 | 不把复杂表单塞入菜单 |
| 同一区域并列内容 | 标签页 | 切换是否自动激活取决于延迟和模式要求 |
| 选择已有值 | 原生选择器或可访问列表选择 | 搜索式组合框需要完整键盘与读屏支持 |
| 可选补充解释 | 提示气泡或展开说明 | 重要说明不依赖悬停 |
| 调整顺序 | 拖放加非拖动替代 | 提供上下移动、目标位置选择等入口 |
| 大量行选择 | 复选框与批量操作栏 | 明确选中当前页还是所有筛选结果 |
| 破坏性操作 | 明确后果的确认或可恢复撤销 | 不能给所有小动作都套确认框 |

具体复杂组件按 [APG 模式目录](https://www.w3.org/WAI/ARIA/apg/patterns/)选取对应模式；不要凭熟悉程度为所有控件复制同一组快捷键。

## 5. 角色、权限与恢复

### 5.1 权限表达

- **隐藏**适合用户不应知道或完全无关的功能；**禁用并解释**适合用户需要理解功能存在、条件或申请路径的场景。安全策略优先于可发现性。
- 页面中的权限提示只是沟通，不是安全边界。不能以隐藏按钮替代服务端授权。
- 区分个人、团队、组织及资源级设置，明确继承值与覆盖值。不要让一个看似局部的开关意外修改整个组织。
- 管理员与普通用户分别验证；禁止用最高权限成功路径代表所有角色。
- 请求访问入口只有在真实可用且授权时才实现，不伪造已发送申请的状态。

### 5.2 恢复优先于堆确认

可可靠撤销的低风险操作通常可以简化确认，但要给足发现和恢复机会。不可恢复、涉及外部影响或高代价的操作应更清楚地呈现对象、范围和后果。

恢复不只是 Toast 里一个按钮，还包括：草稿、版本、垃圾箱、重新上传、重试、撤销窗口、冲突比较、重新认证后返回。只有后端或现有系统支持时才承诺这些能力。不能在 UI 文案里“发明”撤销。

## 6. 高风险页面：清楚优先于转化

涉及支付、法律承诺、健康、身份、账号安全或不可恢复数据变更时，先确认产品已有要求与任务授权。设计优化不授权真实交易、外发、权限改变或生产数据删除。测试使用合成数据、沙箱或已有测试环境。

- 提交前展示具体对象、金额与币种、费用、时间/时区、接收方、作用范围和重要限制。
- 改变对象、金额、条款或风险后重新呈现变化，不沿用先前确认的视觉状态。
- 确认控件用明确动作文字；避免默认焦点或默认键盘提交误触不可逆动作。
- 重要结果提供可追溯标识和后续路径；但不在截图、日志或错误消息中无必要暴露敏感信息。
- 服务端响应不明时，优先查询真实状态再决定恢复，不让“重试”造成重复扣款、发送或创建。
- 不隐藏取消、退出、拒绝、导出或删除路径，不用羞辱性文案迫使用户接受。

[WCAG 2.2 SC 3.3.4](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)针对法律承诺、金融交易、用户可控存储数据变更/删除及测试答卷提交，要求可撤回、检查纠错或提交前审阅确认等至少一种保障。它不等于所有操作都必须弹确认框，也不取代具体业务的更严格要求。

## 7. 无障碍作为完整流程，而非最后加标签

### 7.1 四条可执行检查线

- **能感知**：信息不只依赖颜色、动画、声音或位置；图片有适当替代；重要动态状态能被读屏器获知。
- **能操作**：键盘可完成核心任务，没有非预期焦点陷阱；触摸目标可用；拖放有可行替代；超时有适当处理。
- **能理解**：标签和错误清楚，行为与控件外观一致，输入不会无预警改变上下文。
- **能可靠解析**：优先原生语义；控件有名称、角色与状态；自定义组件按模式实现并用真实辅助技术抽查。

不要为“无障碍”给所有节点加 ARIA，也不要在有可见标签时给出含义相反的 accessible name。视觉标签、程序化名称、语音输入目标应一致。

### 7.2 动态通知

[WCAG 状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)强调：不移动焦点的状态消息也应能由辅助技术获知。

- 搜索结果数量、保存完成、上传进度等用适当状态机制，避免为了朗读每次强行移动焦点。
- 紧急警告才用打断性播报。不要把每个输入字符、每帧进度或所有 Toast 都设为 assertive。
- 更新频繁时合并播报，避免读屏队列被旧消息淹没。错误既要能听到，也要能再次找到和修正。
- 客户端路由后页面标题、主内容定位和焦点策略应可预期，不能只换可见内容却让辅助技术停留在旧页面上下文。

## 8. 心理学启发：生成假设，不包装成必然规律

[Laws of UX](https://lawsofux.com/)与 [Growth.Design](https://growth.design/psychology)适合帮助命名问题和寻找假设。它们是设计知识与案例的整理，不是任何页面必然提升转化的证据。下面是本技能的应用扩展，实际效果必须在当前用户和任务中验证。

| 启发 | 适用问题与可做改变 | 防止误用 | 观察什么 |
|---|---|---|---|
| 选择复杂度 | 将真正不同的选项分组，提供比较维度与合适默认 | 不能为了少选项隐藏重要选择或强推付费方案 | 找到合适选项的成功率、改选与退出原因 |
| 目标大小与距离 | 高频操作靠近其对象，增加可点击范围和适当间距 | 不把危险动作靠近高频动作以求更快 | 误触、移动距离、键盘路径、触摸成功率 |
| 邻近与共同区域 | 让相关标签、值与操作形成清楚组块 | 不把每组都包卡片造成视觉碎裂 | 用户是否正确对应字段、数据与动作 |
| 熟悉的交互预期 | 使用惯常图标、控件与导航行为 | 熟悉不等于永不创新；新模式需解释和验证 | 首次使用误解、错误点击、求助次数 |
| 识别优于回忆 | 在决策点显示上下文、最近使用与已选项 | 不无必要暴露历史或敏感数据 | 用户是否需要来回查找或记忆信息 |
| 渐进披露 | 默认展示当前任务需要的信息，按需求展开复杂选项 | 不藏费用、风险、取消与必填条件 | 任务成功率和发现高级功能的能力 |
| 审美影响感知 | 改善一致性与视觉秩序，减少初始不信任 | 漂亮不能证明功能可用，更不能覆盖风险 | 分别测主观信任与客观任务成功 |

不要套用“人只能记住固定数量”“所有响应必须小于某个神奇阈值”“某个心理效应保证提升 X%”等口号。研究结论需要适用条件、原始来源和可重复证据；没有这些时，将其写成设计假设。

### 8.1 伦理检查

逐条问：用户是否知道正在作什么决定？接受和拒绝是否都容易理解和执行？默认值是否符合用户利益？退出是否比进入无理由地更困难？有没有虚假稀缺、伪造社会证明、隐性续费、强迫连续完成或误导性颜色？

如果短期转化上升却带来更多误购、撤销、投诉或退款，不应判定体验变好。优化指标同时关注任务完成、错误成本、信任和长期可用性。

## 9. AI 与长任务界面的额外边界

- 区分排队、执行、等待外部输入、已停止、部分完成、失败和完成。输出开始流动不代表任务已完成。
- 停止按钮明确停止什么；已经执行的外部动作不能用“已取消”掩盖。
- 部分结果可读、可复制时应标明未完成，后续补写不能让用户丢失阅读位置。
- 引用和证据链接指向支持内容；没有证据时标不确定，不用视觉权威感掩盖猜测。
- 再生成、编辑、重试和执行外部动作分开。不可把“再试一次”暗中变成再次发送或支付。
- 长任务刷新后是否恢复、历史是否保存、输入是否会丢失，应依据真实系统能力设计。

## 10. 用参考站研究流程，而不是复刻截图

[Mobbin](https://mobbin.com/)可帮助观察真实产品的页面与流程。研究时记录目标用户、入口、状态转换、错误处理、退出方式和平台差异；看不到的部分不要补成事实。

每次提炼一个可迁移机制：

1. 参考解决的具体问题是什么？
2. 当前产品是否有相同问题与前置条件？
3. 哪个机制值得借鉴，哪些品牌样式不必复制？
4. 有什么代价，例如步骤更多、信息更密、开发复杂度更高？
5. 怎么用真实任务或可复现测试确认改进？

证据不足时保留小范围、可撤销的修改。不要把流行产品的做法等同最佳实践，更不要根据一张截图声称已验证交互。

## 11. 流程交付模板

对每个核心流程输出：

- **任务与角色**：用户要完成什么、依赖什么条件。
- **路径**：入口 → 关键步骤 → 系统完成证据。
- **状态表**：至少覆盖适用的默认、空、加载、错误、成功及恢复。
- **关键决策**：为什么选择该控件、顺序和反馈，保留了什么权衡。
- **风险与权限**：真实执行会有什么外部影响，测试使用什么安全数据。
- **验收**：正常路径、失败路径、键盘路径与窄屏路径的具体检查。
- **未验证项**：缺少接口、权限、真实设备或用户证据的部分，避免写成完成。

评审时先尝试完成任务，再看页面是否好看。只有流程和视觉两者都成立，才称为可交付的页面优化。
