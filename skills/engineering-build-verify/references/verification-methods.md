# Verification Methods（验证方法目录）

这里是“怎么确认做对了”时可以用的成熟方法。**按事情大小挑，不求全**：大多数常规任务只需要业务验证 + 已有测试 + 代码评审；下面的重型方法只在触发条件真的成立时才用。项目把常用方法写进自己的检查配置，Agent 不临场发明，也不为了显得严谨而堆方法。

每个方法写清：什么时候用、留什么证据、能证明什么、不能证明什么。括号里的代号只用于证据包。

## 业务验证（G4 解决了业务问题吗）——每次都要

| 方法 | 什么时候用 | 证据 | 局限 |
|---|---|---|---|
| 按需求卡演示 | 每次 | 用真实或接近真实的场景，把“做成的样子”逐条走一遍的录屏或记录 | 只覆盖演示到的路径 |
| 找目标用户试 | 新功能、体验明显改变 | 3–5 名目标用户完成指定任务：是否完成、卡在哪、怎么理解的 | 小样本发现方向问题，不证明效果 |
| 业务数据核对 | 涉及金额、库存、统计、报表 | 拿一批真实（脱敏）数据前后对账 | 依赖样本代表性 |
| 上线后看业务指标 | 有发布 | 上线前写下预期（比如转化、投诉、处理时长），上线后对照 | 短期波动多，需要观察窗口 |

## 设计验证（D，写代码之前）——只有重要改动且逻辑复杂时

| 方法 | 触发条件 | 证据 | 能证明 / 不能证明 |
|---|---|---|---|
| TLA+ + TLC 模型检查 | 重要改动的设计涉及并发、分布式协议、重试/幂等、状态机、权限流转、跨服务一致性 | `.tla` 规格、不变量与活性属性、TLC 运行输出（状态数、无反例） | 在有界模型内穷举设计层所有交错行为；**不证明代码实现符合规格** |
| P 语言 | 同上，团队觉得 TLA+ 学习成本过高、偏好状态机写法时 | P 模型与检查结果 | 同上；更接近编程语言，AWS 后续主推 |
| 状态表 / 决策表评审 | 常规改动里的状态逻辑，不值得做模型检查时 | 状态 x 事件 表，非法转换列表 | 覆盖已枚举的情况；不发现未枚举的交错 |

规则：模型检查发现的反例必须转成实现层的回归测试；规格与代码不同步时，以代码测试为准并标注规格过期。

## 工程底线（G0）——每次都要

| 方法 | 触发条件 | 证据 |
|---|---|---|
| build / lint / typecheck / 已有测试 | 每次 | CI run、命令、exit code |
| 依赖与安全扫描（SCA、secret 扫描、SAST） | 每次有依赖、配置或权限相关改动 | 扫描报告与处理结论 |
| React Doctor（React 代码体检） | React 项目的 PR、重构前后、交付前 | `--scope changed` 的 JSON 报告：新引入的问题及处理结论（用法见 `react-doctor.md`） |
| 变异测试（Stryker、mutmut、PIT） | 核心业务逻辑、计费、权限判断等高价值模块；覆盖率高但怀疑断言弱时 | 变更文件的 mutation score 与存活变异 |

变异测试证明“测试会不会发现错误”，能揭示覆盖率 100% 但断言空洞的问题；耗时较长，只对变更范围或核心模块跑。

## 功能对吗（G1）

| 方法 | 触发条件 | 证据 | 局限 |
|---|---|---|---|
| 实例化需求 / BDD（Given-When-Then） | 需求卡里每条“做成的样子” | 验收项 ID -> 可执行例子 -> 运行结果 | 只覆盖写出来的例子 |
| 属性测试（Hypothesis、fast-check） | 纯逻辑、解析/序列化、计算、数据变换 | 属性定义、运行次数、最小化反例 | 属性写错会给出虚假信心 |
| 契约测试（Pact，consumer-driven） | 跨服务或前后端分团队的 HTTP/消息 API | 契约文件、provider 验证结果、can-i-deploy 结论 | 不替代端到端业务验证 |
| API / DB 集成测试 | 持久化、事务、迁移、租户隔离 | 测试记录、迁移前后数据检查 | 依赖测试数据代表性 |
| 负向回归测试 | 权限、租户隔离、输入校验等硬约束 | “不合规会被拒”的测试 | — |

## 用起来顺吗（G2）——有界面时

| 方法 | 触发条件 | 证据 | 局限 |
|---|---|---|---|
| Playwright E2E | 关键用户路径 | trace、录像、通过记录 | 只走脚本里的路径 |
| Bombadil（UI 属性测试） | 状态复杂的 Web/终端 UI；需要验证“永远不出现未处理错误”“加载最终结束”“操作后 N 秒内有反馈”之类不变量 | TypeScript 规约（`always` / `eventually` / `within` 等时序属性 + 动作生成器）、探索运行记录、最小复现 | 随机探索，非穷举；属性需从验收项提炼 |
| 无障碍（`@axe-core/playwright`） | 所有 UI 变更 | 扫描结果 JSON | 自动化只能发现约三到四成 WCAG 问题，关键流程仍需键盘/读屏人工抽查 |
| 视觉回归（Playwright `toHaveScreenshot`） | 布局、组件样式变更 | 基线与差异图 | 只发现像素变化，不判断好坏 |
| UI/UX 规则审计 | 有界面的交付、改版前摸底 | 交给 `engineering-ui-ux-audit`：69 条规则逐条 通过/不通过/不适用/未验证，含证据与复验条件 | 规则来自通用规范和经验，不替代目标用户试用 |
| 状态截图矩阵 | loading / empty / error / 权限不足 / 长文本 / 窄屏 | 每个状态的截图 | — |

Agent 可以直接从需求卡里“做成的样子”起草 Bombadil 属性和 Playwright 用例；由验收人确认属性确实表达了验收意图。

## 看起来对吗（G3）

无成熟工具可替代。做法：

- 检索项目或私有层中同场景、已确认的“之前 vs 之后”案例（含理由和适用场景），验收人写出判断理由并引用案例 ID。客观项（对比度、点击路径长度）归 G2，不混入主观偏好。
- 校准：用未参与提示的 holdout 成对案例评估验收人和 Agent 的判断一致率与严重漏判，据此决定这类判断能不能交给他们。模型输出只是建议。

## 代码评审（CR）

参考 Google eng-practices：

- 先看整体设计是否合理、是否属于这个系统，再看功能、复杂度、测试、命名、注释与风格。
- 被指派的代码逐行看；上下文不足时读整个文件。
- 问题优先、按严重度排序，指出具体文件行号；也指出做得好的地方。
- 评审标准是“整体改善代码健康度”，不是追求完美；不因个人偏好阻塞。

具体口径见 `references/code-review-standards.md`。

## 上线准备（R）

| 方法 | 触发条件 | 证据 |
|---|---|---|
| 上线就绪评审（PRR，参考 Google SRE） | 新服务、重要改动、首次上生产 | 逐项清单 + 每项证据与 owner：容量估算、监控告警、依赖、降级、备份恢复 |
| 分阶段发布（canary / 灰度 / feature flag） | 有部署的变更 | 发布计划、观察窗口、放量与中止条件 |
| 回滚演练 | 有迁移或不可逆数据变更时必需 | 演练记录或已验证的回滚命令 |
| 业务侧就绪 | 有用户可见变化 | 谁要提前知道（客户、客服、销售、运营）、说明与培训、出问题的业务兜底 |
| 发布后复盘 | 重要改动或出现异常 | 预期 vs 实际；线上发现的问题进入“交付后学到了什么” |

清单填完不等于就绪；每项必须附证据。PRR 不重复做代码评审，也不扩展成架构评审。

## 重型方法（默认不用）

| 方法 | 适用 | 代价 |
|---|---|---|
| 确定性仿真测试（FoundationDB 式、Antithesis） | 分布式数据库、消息系统、强一致存储 | 需要按仿真设计系统或接入确定性 hypervisor；老系统改造成本高 |
| Jepsen 式故障注入 | 已有分布式系统的一致性验证 | 黑盒、单次运行慢 |

只有在 D 步骤的模型检查之外仍需验证实现层并发正确性、且有数据丢失风险时才考虑。

## 度量

- 交付：DORA 四项（部署频率、变更前置时间、变更失败率、恢复时间）。AI 辅助会放大既有的强项与弱项：吞吐上升时稳定性可能下降，因此门禁要先于提速。
- 机制本身：首次通过率、重复纠偏率、每个交付占用创始人多少分钟、门禁执行开销。
