# Delivery Gates（交付三关口）

团队交付一件事，只在三个时刻停下来想一想：**开工前想清楚、交付前确认做对了、交付后看看学到了什么**。其余时间正常干活，不额外走流程。

本文件是给 Agent 的工作方法，不是给人填的表。对人说话按 `output-contracts.md` 的“对人表达”规则：先结论，用业务语言，只说相关的事。验证手段见 `verification-methods.md`。

## 0. 先问业务，再谈技术

每个关口都从同一个问题出发：**这件事帮谁、解决什么问题、做成了是什么样子。** 技术检查是为了回答这个问题，不是目的本身。

- 判断“做没做成”，先看业务结果（用户能不能顺利完成那件事、数据对不对、客户会不会受影响），再看代码质量。
- 业务语言优先：说“销售能在客户页直接看到合同状态”，不说“新增合同状态字段并在详情页渲染”。
- 任务越小，流程越轻。小改动一句话说明改了什么、怎么确认没改坏即可。

## 1. 谁负责什么

| 角色 | 一句话 |
|---|---|
| 提需求的人（创始人 / 业务方） | 给方向和底线，只在真正需要取舍时拍板；不负责拆需求，也不负责挑低级错误 |
| 负责人（这件事唯一的 owner） | 把一句话需求想清楚、做出来、证明做对了；能自己定的事自己定并记下来 |
| 验收人（不是负责人本人） | 站在用户和业务的角度复核结果，讲清楚依据；开发用的 Agent 不能当验收人 |

## 2. 这件事有多大

按“做错了代价多大、能不能撤回”分四档，档位决定要多仔细，也决定谁能拍板。

| 档位 | 典型例子 | 谁拍板 |
|---|---|---|
| 小改（L0） | 文案、已知规范内的小修复，随时可撤回 | 负责人自己 |
| 常规（L1） | 常规功能、标准交互 | 负责人 + 验收人 |
| 重要（L2） | 新模块、明显改变用户体验、新服务上线 | 有授权的产品 / 技术负责人 |
| 方向性（L3） | 产品方向、对客户的承诺、做了很难回头的事 | 创始人或正式授权人 |

涉及安全、权限、客户数据、合规的，不论多小都不能按“小改”处理。拿不准档位时往高一档走。

## 3. 开工前：想清楚（Intent）

目标：负责人用自己的理解把需求讲清楚，**让提需求的人看一眼就能说“对”或“不对”**，而不是把一堆问题丢回去。

1. 原话保留。别用自己的转述覆盖对方的意思。
2. 先自己查：现有产品、数据、类似的历史任务和案例。能查到的不问。
3. 写一页需求卡，回答五件事：
   - 帮谁、在什么场景下、解决什么问题；
   - 做成了是什么样子（用户能做到什么、看到什么，写成可以当场演示的结果）；
   - 这次不做什么；
   - 哪些是确定的、哪些是我的推测（推测要能撤回）、哪些还不知道；
   - 档位，以及打算怎么证明做对了。
4. 能演示就别只写字：小改给一个前后例子，界面给可点的原型或预览，新模块给一条走通的主流程。
5. 低风险、可撤回的选择自己定，写一句理由就行。

**什么时候找提需求的人：** 只有遇到价值取舍、做了难回头、涉及关键客户、风险大或超出自己授权时。找的时候带上：冲突是什么、查过什么、2–3 个选项和各自代价、你推荐哪个、具体需要对方决定什么、不等决定哪些可以先做。不为这个开会，非紧急的攒一起问。

## 4. 交付前：确认做对了（Quality）

目标：**不合格的东西不出现在提需求的人面前。** 验收人按下面的顺序在心里过一遍，只深挖跟这件事相关的项；无关的一句话带过，不必逐项列出来。

1. **解决了业务问题吗？** 对照需求卡的“做成了是什么样子”，用真实或接近真实的场景走一遍。这一条最重要，先看。
2. **功能对吗？** 每条“做成的样子”都有对应的证据：测试、演示录屏、数据核对。
3. **用起来顺吗？** 有界面时：加载、空数据、出错时用户知道发生了什么、能不能恢复；不同屏幕和键盘操作。
4. **看起来对吗？** 跟公司认可过的同类案例比：重点是否突出、信息是否太密或太散、交互是否顺手。这是判断题，由校准过的人做，Agent 只给参考意见。
5. **工程底线守住了吗？** 能编译、原有测试没坏、没有安全和依赖问题、代码经过评审。
6. **上线准备好了吗？**（有发布时）见第 5 节。
7. **设计本身靠谱吗？**（重要档以上，且涉及并发、多步骤状态、权限流转时）上线前就该在设计阶段验证过，这里确认结论还成立。

### 怎么下结论

- 结论只有三种：**可以交付**、**还不能交付（附原因和最小修改建议）**、**缺证据没法判断（说清楚缺什么、谁来补）**。
- 没有证据就不算通过。证据要对应这次真正要交付的版本；改过之后受影响的部分重新确认。
- 不能用假数据、截图或“开发说测过了”代替真实验证。
- 特殊情况要放行，只能由有权限的人决定，并写清楚理由、期限和补救办法；安全和合规问题不能这样放行。
- 同一类低级错误第二次出现，就把它变成自动检查，而不是靠人每次盯。

### 留下的证据

交付时留一份证据包（`schemas/evidence-package.schema.json`），可以用 `gate_check.py`（源仓库 `scripts/` 下）自动检查是否齐全。证据包给工具和追溯用，对人汇报时只说结论、阻断项和需要谁做什么。

## 5. 上线：业务和技术都要准备好

上线不只是技术动作。有发布时确认：

- **业务侧**：谁需要提前知道（客户、客服、销售、运营），说明和培训是否就绪；数据口径是否变化；出问题时业务上怎么兜底。
- **技术侧**：分批放量还是一次上线；上线后看哪些指标（业务指标优先，比如下单量、转化、投诉）；出问题怎么撤回，撤回方法是否验证过。
- **上线后**：对照预期看一眼实际效果；线上发现的问题记下来，进入第 6 节。

## 6. 交付后：学到了什么（Evolution）

大多数任务**不需要沉淀**，直接结束。只有当一个问题很可能再发生、或者代价很高时，才值得记下来。

| 发生了什么 | 记到哪里 |
|---|---|
| 需求理解偏了 | 项目里的需求卡样例 |
| 审美 / 体验上有分歧 | 一对“之前 vs 之后”的案例，写清为什么、什么场景适用、什么场景不适用 |
| 同类技术或安全错误又出现 | 变成自动检查或测试 |
| 工具、环境老出问题 | 修工具或环境脚本 |
| Agent 的做事方法有缺陷 | 本仓库的 lesson（先开 issue，见 `self-evolution-harness.md`） |
| 分工、交接卡住 | 调整授权或交接约定 |

记下来的东西要有：发生了什么的证据、适用和不适用的范围、怎么验证有效、谁维护。用不上了就删掉，不只增不减。结构见 `schemas/evolution-candidate.schema.json`。

## 7. 公司自己的东西放哪

本仓库只放通用方法。**公司和项目的审美案例、需求样例、各项目的检查配置、任务记录和指标**放在项目里的 `.evolution/` 或私有资产仓库（环境变量 `EE_PRIVATE_ASSETS` 指向的目录），不进本仓库，也不进公开 issue。

查找顺序：项目 `.evolution/` → `EE_PRIVATE_ASSETS` → 都没有就按通用方法做，并说一句“没有加载公司案例”。每次只取最相关的 2–5 条，不整库塞进上下文。项目检查配置的结构见 `schemas/gate-profile.schema.json`。

## 8. 其他约定

- 三个关口按“一件事的生命周期”触发，不是每轮对话都触发；同一件事中断后恢复，从停下的地方继续，不重走已完成的关口。范围变了就回到“想清楚”，更新需求卡版本。
- 小改可以把“想清楚”和“做”合在一起：一句话说明 + 确认没改坏。但安全、数据、权限相关的检查不能省。

代号只出现在证据包、检查配置和工具输出里，对人说话不用。

| G1 | 功能对吗 |
