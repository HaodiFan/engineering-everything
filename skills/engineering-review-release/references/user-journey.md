# User Journey–Driven Review（产品认知与用户旅程审查）

本文件解决一个常规代码评审与 UI 规范检查覆盖不到的盲区：**代码零 Bug、测试全绿、视觉也精致，但产品本身按系统模块而不是按用户工作方式组织，导致整体设计方向就是错的。**

---

## 1. 六层评审模型（L0–L5）

| 层级 | 维度 | 核心问题 | 主要覆盖手段 |
|---|---|---|---|
| **L5** | **User Journey** | 产品是否按用户实际做事的方式组织？ | **本文件（Expected vs Actual Journey + Blind Walkthrough）** |
| **L4** | **Product Logic** | 功能组合、信息架构、决策时机是否合理？ | **本文件（8 大 Product Anti-pattern）** + `RV-BIZ-01..05` |
| **L3** | **Interaction** | 操作、导航、反馈、异常状态是否顺畅？ | `bombadil.md` + `ui-ux-rules.md` |
| **L2** | **Visual** | 视觉层级、排版、组件、对比度是否合理？ | `ui-ux-rules.md` + `UX-VIS-09` + 公司审美案例 |
| **L1** | **Functional** | 既定功能与验收标准是否正确工作？ | `RV-BIZ-02..04` + 端到端/回归测试 |
| **L0** | **Engineering** | 构建、测试、代码质量、坏味道、安全是否合格？ | `RV-BASE-*` + `RV-BUG-*` + `RV-SMELL-*` + `RV-SEC-*` + React Doctor |

**核心原则**：技术测试（TLA+ / Bombadil / Playwright / React Doctor / 单元测试）验证的是**“实现是否符合既定规格”**；Journey Review 验证的是**“规格和产品组织方式本身对不对”**。

---

## 2. 触发边界（严格防膨胀）

**不要对所有改动都跑完整旅程审查。**

- **必须触发**（`has_journey_surface = true`）：
  - 新增面向用户的功能模块、核心工作流或端到端任务；
  - 导航结构、信息架构（IA）、Tab/侧边栏组织、首页或工作台（Dashboard / Workspace）调整；
  - 多步骤向导、跨页面/跨角色协作流程、审批流、异步/AI 长任务与通知回流；
  - 需求卡（`intent-card`）显式声明了 `journeys[]`，或人工开启 `--journey`。
- **不触发（`AUTO_NA`）**：
  - 纯文案润色、纯样式/间距/颜色/图标微调；
  - 不改变用户路径的内部代码重构、依赖升级或纯后端性能修复；
  - 局部 bugfix 且不改变信息架构与任务顺序。

## 3. 轻量 Journey Contract（开工前写入需求卡）

在 `engineering-product-definition` 阶段写需求卡（`schemas/intent-card.schema.json` 的可选 `journeys[]` 字段）时，**先推导核心用户旅程，再决定页面、Tab 和功能模块**。

```yaml
journey:
  id: submit-industry-signal
  actor: enterprise-employee
  trigger: 发现有价值的行业信息
  goal: 让企业获得并分析该信息，并在需要时参与决策
  stages:
    - 提交信息
    - 确认已被系统接收
    - 在后台持续处理（不阻塞其他工作）
    - 获取分析结果与依据
    - 必要时作出决策并获得执行反馈
  success:
    - 信息进入企业分析流程且可追踪
    - 用户能获知结果并在需要时完成决策
  experience_constraints:
    - 不要求用户理解系统内部模块划分
    - 异步处理期间不阻塞其他工作
    - 中断或切换页面后能恢复上下文
    - 需要决策时主动明确通知并附上决策依据
```

> **红线**：Journey Contract **刻意不写页面名、Tab 名、按钮文案和内部模块名**。只有与实现解耦，Reviewer 才能独立判断当前产品方案本身是否合理，而不是被开发者现有设计锚定。

---

## 4. 防锚定评审顺序（Journey-First Protocol）

当改动命中旅程触发条件时，必须按以下 4 步顺序判断：

1. **Expected Journey（先独立推导）**：仅根据 `actor / trigger / goal / constraints`（JTBD + 分层任务分析 HTA），在看页面或源码之前，写出用户“本来应该如何完成目标”的合理阶段。
2. **Actual Journey / Blind User Walkthrough（无引导真实走查）**：
   - 给独立 Reviewer Agent **仅提供**：用户身份与背景、真实场景、任务目标、产品入口 URL 与必要测试账号。
   - **严禁提前提供**：git diff、源码文件列表、按钮位置、开发者预设路径或内部模块关系说明（`scripts/review_runner.py` 会自动生成剥离代码上下文的 `ui_ux_experience.blind.md`）。
   - Reviewer 实际操作产品，逐条记录真实路径与 **7 项观察点**：
     1. `entry_clarity`：第一次看到界面时，是否知道从哪里开始？
     2. `action_discoverability`：能否不靠提示独立发现正确操作？
     3. `module_burden`：是否被迫理解产品内部模块划分才能找到入口？
     4. `async_non_blocking`：异步/AI 处理等待期间能否继续做其他工作？
     5. `context_recovery`：跨页、中断或分析完成后能否找回上下文？
     6. `next_step_clarity`：每完成一步后是否明确知道下一步该做什么？
     7. `goal_achieved`：最终是否真正达成了用户目标（而非仅仅“点了按钮”）？
3. **Journey Gap Analysis（旅程差异与 8 大反模式排查）**：对比 Expected Stages 与 Actual Steps（步数、跳转次数、上下文切换、信息缺口），逐项核查下方 8 类 Product Anti-pattern。
4. **既有细项检查**：继续完成 Bombadil 状态探索、陌生语言自解释（`UX-VIS-09`）、14 组 70 条 `UX-*` 规则与工程检查。

> **证据边界**：Agent 的 Blind Walkthrough 是高效的**第一道认知筛查代理观察**，不能替代真实用户的可用性测试（`UX-RES-*`）。仅有静态截图时，无法操作验证的观察点必须如实标 `UNVERIFIED` 并记入 `unverified_items`。

## 5. 八类 Product Anti-pattern（`AP-01`..`AP-08`）

| 编号 | 反模式 | 判定标准 | 典型症状 |
|---|---|---|---|
| **`AP-01`** | **Module-Driven UI**（模块驱动界面） | 界面按后端/技术模块平铺，而非按用户工作任务组织 | 每个模块都有独立 Tab，但没有围绕当前任务的主工作线 |
| **`AP-02`** | **Broken Journey**（旅程碎片化） | 用户必须自行在多个页面/Tab/功能间来回跳转拼接流程 | 收通知 → 进任务 → 查知识库 → 回任务提交 → 进动态确认（7 步本可 3 步） |
| **`AP-03`** | **Context Loss**（上下文丢失） | 跨页面、跨会话、跨角色或异步返回后丢失上下文，或被迫重复输入 | 点进详情返回筛选清空、审批时看不到上游单据、多步反复填相同信息 |
| **`AP-04`** | **Wrong Sequence**（步骤顺序违背自然工作流） | 产品强制要求用户按系统便利而非人类直觉的顺序操作 | 还没看内容就要先选分类归档、未确认对象就先填配置 |
| **`AP-05`** | **Premature Decision**（过早/盲目决策） | 在用户掌握必要依据或后果前就要求做决定，或关键信息提交后才露出 | 审批按钮旁边没有金额/依据/风险，点完提交才弹出约束或费用 |
| **`AP-06`** | **Missing Next Action**（主入口或下一步缺失） | 首次到达不知道从哪开始，或完成一步后页面陷入死胡同 | 首页视觉精致却找不到主任务入口；提交后只闪过 toast 无后续指引 |
| **`AP-07`** | **Cognitive Overload**（内部复杂性转嫁 / 流程阻塞） | 要求用户理解系统内部状态/术语/流程，或异步任务阻塞其他工作 | AI 分析时全屏 modal 锁死页面；暴露内部 queue/worker 概念让用户手工触发 |
| **`AP-08`** | **Frequency Mismatch**（高低频权重错位） | 高频核心任务被深埋在二级菜单，低频配置占据主交互空间 | 每天处理 50 次的待办藏在角落，一年用一次的系统设置占满首屏 |

**严重度判断**：阻断核心业务目标或造成高风险误决策的标 `P1`（阻断）；明显增加用户组织成本与返工的标 `P2`（建议优化）；局部效率微调标 `P3`。注意与 `UX-FLOW-03` 协同：**减少步数不是唯一目标，高风险确认、费用核对与必要审阅绝不能为了省步骤而删除。**

## 6. 防过度审查护栏（正例放行原则）

提高发现产品设计错误的能力，**绝不能变成“为了找问题而推翻合理设计”**：

- **标准专家/后台工作台正例**：如果一个标准 B2B 后台、列表筛选、批量操作或分模块导航本身就贴合目标用户（如运营、财务、运维）的高频工作习惯（快速检索、多对象比对、批处理），**必须正常判 `PASS`**，不得机械套用 `AP-01` 强行要求改成“单主线信息流”或“对话式界面”。
- 任何一条 `AP-01..08` 判定为 `FOUND`，必须同时给出：**具体受影响的用户目标 + 可观察的实际路径/卡点证据 + 更符合用户旅程的最小重组建议**；只说“感觉不够顺”或套用个人风格偏好一律无效（同 `UX-META-04`）。
