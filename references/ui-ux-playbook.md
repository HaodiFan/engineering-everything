# 评判输出与可选实施

默认产出是评判报告，不是教程练习，也不是自动改代码。只有用户要求把参考拆成任务单，或授权实施时，才使用后半部分模板。

## 1. 评判报告结构

- **范围和限制**：页面或流程、角色、设备与视口、语言、材料（可运行产品 / 原型 / 录像 / 截图）、是否允许改代码。
- **主任务**：用动词写清要完成什么，以及什么叫成功。
- **发现**：按阻断、严重、一般、建议排序。每条包含位置、规则 ID、结论、严重度、可观察问题、证据或未验证原因、修复建议、复验条件。
- **UI 自解释检查**：单列 `UX-VIS-09` 的原版/陌生语言版、给定任务、观察者熟悉度、视觉线索与操作结果；未做转换或仅有截图时如实标明未验证范围。
- **通过与不适用**：可附简表，避免只报问题造成范围不清。
- **未验证项**：焦点、路由、提交、性能、读屏、权限实装等因材料不足不能下结论的规则。
- **待执行研究**：对应 `UX-RES-01` 至 `UX-RES-03`，不写成已经访谈或已经测试。

不要输出综合分、审美分或未经实验的转化承诺。

### 发现写法对照

弱：「首屏不够高级，建议增加留白和动效。」

可评判：「筛选标签与结果列表的间距和标签组内间距相同，难以区分两组（`UX-VIS-05`）。建议保留标签内部紧凑间距，加大筛选区与结果区距离，并在结果标题显示数量。复验：窄屏和两行标签时分组仍清楚，且筛选区没有占满整屏。返回是否保留筛选见 `UX-IA-02`，本材料为截图，该项未验证。」

## 2. 可选：从参考提取机制

需要借鉴上线案例时，用下面的拆解卡，不要整站照搬品牌和素材。

- 任务：谁在什么场景要完成什么；失败或离开后怎么办。
- 证据：链接、步骤、视口、状态；只记录完成了的观察。
- 机制：哪一个具体做法可能有用。
- 代价：同一做法会增加什么。
- 适用范围：什么页面适合，什么条件不应使用。
- 落地：改哪个组件、状态或文案；保留哪些令牌。
- 验收：可复现场景；效果依赖用户行为时约定观察方法，不把推断写成结果。

无法访问的交互标未验证，不要从一张参考截图声称已验证交互。第三方 DESIGN.md 不是品牌官方规范。

## 3. 可选：授权实施后的验收句式

在 [宽度/设备]、[数据或前置条件] 下，从 [入口] 完成 [动作]，应看到 [可观察结果]；失败时应 [保留/提示/恢复]；用 [键盘/返回/刷新/重试] 复测，保证 [既有行为] 仍成立。

实施时沿用现有品牌、令牌与组件，只改任务涉及的范围，保留接口、权限和埋点语义。交付须写明改了哪些文件、为何是最小方案、测了什么和未测什么。不要为视觉统一重写公共架构。数值不要把历史项目的像素值升级为全局标准。

## 4. 可选：把已确认决策写入项目文档

只有用户要求沉淀项目设计决策时才新增或更新。若仓库已有设计文档，先适配原位置和格式。下面不是已批准的设计值。

```markdown
# [项目] 界面约束
- 使用场景：[用户、常见设备、高频任务、关键风险]
- 阅读顺序：[首要信息、主要动作、辅助信息]
- 现有设计系统：[组件目录、令牌文件、品牌约束]
- 排版与布局：[角色、密度、重排触发条件、真实长内容]
- 颜色：[背景、文字、边框、行动、错误和成功的语义令牌]
- 状态与反馈：[加载、空白、无结果、错误、成功，及如何恢复]
- 交互：[键盘、焦点、返回与刷新、减少动态效果]
- 验收：[用什么数据、设备、动作复现，以及预期看到什么]
- 已验证例外：[哪个页面、为什么例外、谁确认]
```

文件存在并不保证工具会自动加载；第三方对品牌网站的归纳也不等同于官方规范。
